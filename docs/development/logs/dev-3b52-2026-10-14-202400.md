## Design decisions (I3)
1. Undo unit = one `edit_commit.commit` = one STEP; a GROUP = all steps of one write context (REST request / WS event / worker thread, e.g. a whole Calibrate Synthesis pass) or one explicit `groupId` (X-Pianoid-Group / WS groupId: consecutive steps with the same groupId merge); batches and multi-pitch edits are one commit = one step. MIDI CC streams (source midi_cc) on the same domain+keys within 1 s merge into one group (knob / pitch-wheel sweeps).
2. One linear undo stack + redo stack PER LIBRARY ENTRY, GLOBAL across sources and clients (fe / rest / ws / assistant / calibration / midi_cc) - the assistant needs full control. A new recorded group clears that entry's redo stack.
3. Undo = the latest group of the ACTIVE entry; optional `domains` filter = the latest group touching those domains (the per-editor buttons), refused 409 `history_conflict` if a LATER group touched the same (domain, key) (linear-history check). Redo = the latest undone group (same filter).
4. The inverse is applied THROUGH the machinery: `pianoid.apply_parameter_request(ParameterUpdateRequest(kind, before))` -> edit_commit.commit (read-only guard, Layer B policy, journal) under write context kind `undo` / `redo` (new SOURCE_KINDS), so it broadcasts `state_changed` and every tab follows via I2 (the initiating tab too: kind != 'fe'). Replay never records new history.
5. FE: global Undo / Redo (ToolBar buttons + Ctrl+Z / Ctrl+Shift+Z / Ctrl+Y, not inside text inputs) call the backend; the per-editor Undo / Redo buttons are RE-POINTED to the backend with the editor's domains (proposal §6). The local editor histories stop driving undo (they keep recording External steps as views) -> no double undo.
6. Invalidation: an entry's stacks are cleared on `preset_changed` load_full / load_structural / unload (all entries on load_full: the library is rebuilt); kept across `switch` (per entry) and load_hot / save / spawn.
7. Read-only originals: no edits -> no history; undo/redo on an original -> 409 preset_read_only (up-front, write_routes `param`).
8. Not undoable (exempt, listed in undo_history.EXEMPT with reasons): runtime live sliders (`runtime`), `output_level` (re-run calibration), session state (session_changed), preset lifecycle, coarse `domain_invalidated` / calibration_curve / calibration_reference. Undoable: every preset parameter domain + `excitation_energy` + `deck_feedback_coefficient` (the stored "Set" baseline). A guard test fails on a journaled domain that is neither.
9. Bounds: 200 groups per entry; memory budget 64 MB total (estimated 40 B per stored number, oldest groups evicted first across entries); a step whose `before` cannot be captured completely becomes a BARRIER (undo stops there with 409 history_irreversible).
10. Surface: REST `POST /history/undo {domains?}`, `POST /history/redo {domains?}`, `GET /history` ({entry, can_undo, can_redo, undo:[labels], redo:[labels], depth}); event `history_changed` (same payload, emitted after every push / undo / redo / clear). No WS write event (the REST routes are attributed like any write).
