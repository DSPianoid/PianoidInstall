## Local Review Findings (ranked)

### Critical

**C1. Choosing "Auto" while a port is playing stops the synthesis engine.** Confidence: 90, verified by reading the code.

`PortController._begin_auto()` calls `self.listener.stop()` whenever `listener.port_index is not None`. `MidiListener.stop()` (pianoidMidiListener.py:106-112) closes the port and then runs:

```python
if self.p is not None:
    self.p.pianoid.stopApplication(True)
```

The unified listener is built as `MidiListener(parent=self)`, where `self` is the `Pianoid`. So `self.p.pianoid` is the pianoidCuda engine, and `stopApplication(True)` ends its main loop.

This is reachable in three ways:
- `POST /midi/select_port {"port":"auto"}` from a manual or forced port.
- The new Tunner "Auto" menu item. Its explicit `onClick` re-detects even while already in `AUTO: <port>` state, so in practice any Auto click once a port has been detected.
- The `midi.select_port` path from any assistant or REST caller.

The unit tests miss it because `test_midi_port_select.py`'s fake listener has a harmless `stop()`.

**Fix:** release the port without calling `stop()`. For example, close `listener.midi_in` and set `port_index = None`, or add a `MidiListener.close_port()` that has no engine side effect. Add a test that fails if `stopApplication` is reached.

### High

**H1. Auto-detect on the AMC-10 will pick port 1 (`AMC-10`) on any pedal press, but keys are only proven on port 2.** Confidence: 70 (likely).

The measured facts:
- Ports 1 and 2 carry identical CC streams.
- `MidiPortTaps.poll()` returns records in port-index order.
- `min(hits)` breaks priority ties by record position.

So a pedal press, which is often the first "meaningful" input a pianist makes, moves CC#0 on both ports in the same poll, and port 1 wins. Whether port 1 carries the keys is UNMEASURED (the session log and MIDI_SYSTEM.md both say so).

Separately, `keyboard_name` (`split()[0]`) differs between the ports ("AMC-10" vs "MIDIIN2"), so `set_keyboard` loads a different YAML keyboard config.

In auto mode this repeats at every preset load, because the listener is rebuilt and nothing auto-picked is persisted. The headline user scenario (the AMC-10 in auto mode) is therefore unverified and plausibly broken.

**Before merge:** do a live key check on port 1. If port 1 has no keys, prefer note-on ports, or merge the device's ports as the doc suggests.

**H2. Default-settings regression for a spec-compliant CC64 pedal.** Confidence: 80 (verified by logic).

The hysteresis (down at >= 74, up at <= 54) applies to every user, including the default `sustain_cc = 64` and `polarity = normal`. MIDI 1.0 defines 64-127 as "on", and the engine's own switch is at 64 (MIDI_SYSTEM.md "a switch at the MIDI threshold"). Two cases change for the worse:
- A device that sends "on" as any value from 64 to 73 (some controllers and half-damper pedals with a shallow press) no longer engages sustain from the up state.
- A continuous pedal's release point moves from < 64 to <= 54.

Switch pedals that send 0/127 are unaffected.

**Suggestion:** keep the MIDI threshold for going down (>= 64) and put the hysteresis only on release (for example up at <= 50). Alternatively, apply hysteresis only to a remapped or continuous source. Either way, document the decision. The deferred `test_midi_player` expectation (127/64/0 gives 127/127/0) only covers 64 arriving from the down state.

### Medium

- **M1. Failed port switch leaves a dead listener with a misleading state** (Patch #1). The 409 doc says "A refused request persists nothing", but a request that is queued and then fails in the loop still persists `input_port`.
- **M2. The scan never retries a port it could not open** (Patch #2). This is a likely reload race with the previous listener.
- **M3. `input_port` has three write paths with inconsistent normalization, and `POST /midi/input` does not move the live port** (P1 #1). Recommendation: normalize to `base_name()` in `validate_settings` or `update`, so one canonical form is stored.
- **M4. Not all the verification ran.**
  - The live press check for part 1 is still pending: the user did not press in either window, so the hysteresis has only been tested by capture replay.
  - Part 2 has had no live check at all.
  - These suites were deferred: `test_midi_player`, `test_backend_midi_ingress`, and the 2 `test_load_settings` route tests.
  - Per the verification-surface rule, the change is not verified on its surface: live MIDI on the user's device.
- **M5. The migration can pin the wrong port.** Confidence: 55, likely. `migrationTarget` copies whatever localStorage `midiDefaultPortName` the old FE starred into a manual `input_port`. If the user had starred `UMC1820 MIDI In 0`, the migration would bring back the exact "always UMC1820" complaint, now persisted on the backend. Check the user's browser value before release, or skip migrating to a port that is not currently sending.

### Low

- **L1.** `REST_API.md` `polarity` bullet still says "before the engine's switch at 64". It should mention the hysteresis.
- **L2.** The `midi_start` docstring still says "default 0" (Patch #3). In `long_running_procedure`, the log line `MIDI listener active (unified mode, port None)` prints None in auto mode.
- **L3.** `schemas/commands/playback.json` `midi.set_input_settings` has `additionalProperties: false` and no `input_port`. That is consistent if intentional (the assistant cannot set the port), but it should be stated.
- **L4.** MidiComponent `selectValue` shows "Auto" when the manual port's index is out of range, which hides a disconnected saved port. The chip text is fine.
- **L5.** `map_message` reads `self.settings` twice per message, so a reading can be torn across a concurrent `update()`. This is harmless (it lasts one message), and settings are swapped atomically. Thread safety is otherwise fine:
  - `PortController` runs only on the listener thread.
  - `port_state` is replaced whole.
  - The `_midi_port_request` handoff is under `_midi_port_lock`.
- **L6.** The MIDI_SYSTEM.md section and the session log are thorough and consistent with the code: DMC, measured thresholds, and the open port-1 question.

### Checked and OK

- **Polarity and channel mapping.** `is_sustain_source` uses `(status & 0x0F) + 1 == channel`, which matches 1-16 numbering. Inverted gives `127 - v`, then hysteresis, then CC64 127/0.
- **Non-source CC64 is dropped.** This is intended. With the defaults (`cc 64`, `channel null`) every CC64 is a source, so nothing is dropped.
- **`midi_port` removed from `INHERITABLE`.** The `/load_preset` and `/midi/start` explicit-only parsing is correct, and docs and schema were updated to match.
- **The old FE applier race is gone.** Before, select_port was only re-posted if the listener was already listening.
- **Old-backend compatibility of the migration.** An unknown key gets a 400, the key is kept in localStorage, and the migration retries.
